# Gym Management System — Backend

Production-oriented FastAPI backend for a gym management system, designed to be
consumed by a Flutter mobile app. PostgreSQL is the source of truth; Redis backs
rate limiting, WebSocket pub/sub, and caching.

Payments are cash-only by design: membership payments are confirmed in person by
an admin, and store orders use cash-on-delivery. There is no online payment
gateway and no check-in/attendance system (the digital member card is purely
informational).

## Stack

Python 3.12+, FastAPI, SQLAlchemy 2.x (async, asyncpg), Alembic, Pydantic v2,
PostgreSQL, Redis, Argon2id password hashing, RS256 JWTs, pytest.

## Project layout

```
app/
  core/            config, database, security (hashing/JWT), permissions (RBAC + ownership),
                   exceptions, logging, pagination, rate limiting, redis
  models/          SQLAlchemy models, one module per domain
  schemas/         Pydantic request/response models
  repositories/    generic CRUD base repository
  services/        business logic (auth, memberships, workouts, store, promotions, ...)
  api/v1/endpoints/ FastAPI routers, one per domain
  websocket/       chat WebSocket with Redis pub/sub fan-out
  storage/         local disk / S3-compatible upload storage abstraction
  tasks/           background jobs (membership expiry sweep)
  utils/           upload validation, etc.
migrations/        Alembic environment + versioned migrations
tests/
  unit/            no DB required (security, promotion math, upload validation)
  integration/     require Postgres + Redis (auth flows, memberships, store, classes, workouts)
  security/        RBAC / IDOR / BOLA regression tests (require Postgres + Redis)
scripts/           JWT keypair generation, admin bootstrap
```

## Run instructions

### 1. Docker (recommended)

```bash
cp .env.example .env
python -m scripts.generate_jwt_keys   # writes ./secrets/jwt_private.pem + jwt_public.pem
docker compose up --build
```

This starts Postgres, Redis, and the API (which runs `alembic upgrade head` on
boot before starting uvicorn). API is at http://localhost:8000, docs at
`/docs`.

This `docker-compose.yml` is for **local development only** (it publishes
Postgres/Redis ports to the host and has no TLS). For a real internet-facing
deployment, use `docker-compose.prod.yml` instead — see **[DEPLOYMENT.md](DEPLOYMENT.md)**
for the full walkthrough (server setup, DNS, automatic HTTPS via Caddy,
secrets, backups).

Bootstrap the first admin account (no public API can create one):

```bash
docker compose exec api python -m scripts.create_admin
```

### 2. Local development (without Docker)

```bash
python -m venv .venv
.venv/Scripts/activate        # or `source .venv/bin/activate` on Linux/macOS
pip install -e ".[dev]"

cp .env.example .env
python -m scripts.generate_jwt_keys

# Start Postgres + Redis only:
docker compose up -d postgres redis
# (or point DATABASE_URL / REDIS_URL in .env at your own instances)

alembic upgrade head
python -m scripts.create_admin
uvicorn app.main:app --reload
```

### Tests

Unit tests need nothing but the Python environment:

```bash
pytest tests/unit -v
```

Integration and security tests need a throwaway Postgres + Redis (the same
`docker-compose.yml` services work — point `TEST_DATABASE_URL` at a separate
database so tests never touch your dev data):

```bash
docker compose up -d postgres redis
createdb -h localhost -U gym gym_test
TEST_DATABASE_URL=postgresql+asyncpg://gym:gym@localhost:5432/gym_test pytest tests/integration tests/security -v
```

Test schema is created/dropped per-session directly from SQLAlchemy metadata
(faster than running Alembic per test run); the migration file itself is
verified separately (see below).

### Lint / format / type-check

```bash
ruff check app tests scripts
ruff format app tests scripts
mypy app
```

### Verifying the Alembic migration without a live database

The initial migration's DDL was generated by compiling the SQLAlchemy models
directly against the PostgreSQL dialect (no live connection needed) and can be
sanity-checked the same way at any time:

```bash
alembic history               # shows: <base> -> 0001 (head)
alembic upgrade head --sql    # renders full DDL without touching a database
```

Apply it for real with `alembic upgrade head` against an actual database.

## Environment variables

See `.env.example` for the full list. Highlights:

- `DATABASE_URL` — `postgresql+asyncpg://...`
- `JWT_PRIVATE_KEY_PATH` / `JWT_PUBLIC_KEY_PATH` — RS256 keypair (generate with
  `python -m scripts.generate_jwt_keys`, or `openssl genrsa`/`openssl rsa`).
  Never commit these.
- `JWT_ISSUER` / `JWT_AUDIENCE` — validated on every token.
- `ACCESS_TOKEN_EXPIRE_MINUTES` / `REFRESH_TOKEN_EXPIRE_DAYS`
- `CORS_ORIGINS` — comma-separated, no wildcard in production
- `STORAGE_BACKEND` — `local` or `s3`; local serves uploads from `/uploads`
- `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` — used only by
  `scripts/create_admin.py`
- `PUSH_PROVIDER` — `none` (default, no-op) or `fcm`

## Security summary

- **Auth**: Argon2id password hashing; RS256-signed JWTs with `sub`, `role`,
  `token_type`, `jti`, `iat`, `exp`, `iss`, `aud` all validated on every
  request; the allowed algorithm is fixed server-side (no algorithm
  confusion). Access tokens are short-lived; refresh tokens rotate on every
  use and are stored only as a SHA-256 fingerprint, keyed by a `family_id` —
  presenting an already-rotated (revoked) refresh token revokes the entire
  family (reuse/theft detection).
- **Registration**: public `/auth/register` has no `role` field at all, so a
  client cannot mass-assign itself ADMIN/TRAINER. Staff accounts can only be
  created by an existing admin (`POST /admin/staff`) or the offline
  `scripts/create_admin.py` bootstrap script.
- **Authorization**: role dependencies (`require_admin`, `require_role(...)`)
  are combined with ownership checks (`get_accessible_member_profile`,
  `is_member_assigned_to_trainer`) on every per-resource endpoint. A
  member/trainer probing another member's id gets a 404, not a 403, so the
  response doesn't confirm the id exists.
- **Payments/pricing trust boundary**: membership payment confirmation and
  order status transitions are admin-only server actions; the client can never
  set payment/order status directly. Cart/checkout pricing (unit price,
  discounts, totals) is always recomputed server-side from the current
  `Product`/`Promotion` rows — the client only sends `product_id` + `quantity`.
- **Concurrency**: class booking and stock decrement both take a row lock
  (`SELECT ... FOR UPDATE`) before checking capacity/stock and writing, so two
  simultaneous requests for the last seat/unit cannot both succeed (see
  `tests/integration/test_classes.py::test_concurrent_booking_only_one_gets_last_seat`
  and `test_store.py::test_concurrent_checkout_only_one_wins_last_unit`).
- **Uploads**: images are re-validated by sniffing actual content (Pillow),
  never trusting the client's Content-Type header or filename/extension; a
  random filename is always generated; size is capped.
- **Rate limiting**: Redis-backed fixed-window limiter on login, register,
  refresh, password reset, and chat send, so limits hold across multiple app
  instances. This keys off `request.client.host`, which is only the *real*
  client IP if uvicorn is told to trust your reverse proxy/load balancer —
  the Docker image runs with `--proxy-headers`, and you must set
  `FORWARDED_ALLOW_IPS` to your proxy's address/CIDR in production
  (it defaults to `127.0.0.1`, i.e. no proxy trusted, direct exposure).
  Without this, every request behind a proxy looks like it comes from the
  proxy's IP and all clients would share one rate-limit bucket.
- **Audit logging**: sensitive admin actions (staff creation, membership
  payment confirmation/extension/cancellation, order status/payment changes,
  member activation/trainer assignment) are recorded to `audit_logs` with
  before/after snapshots — never passwords or tokens.
- **Errors**: centralized handlers return a consistent `{"error": {"code",
  "message"}}` shape; unhandled exceptions are logged server-side and never
  leak stack traces to the client.

## Flutter integration notes

- **Base URL**: all application routes are under `/api/v1`; health checks are
  at the root (`/health`, `/health/live`, `/health/ready`).
- **Login**: `POST /api/v1/auth/login` → `{access_token, refresh_token}`. Send
  `Authorization: Bearer <access_token>` on every subsequent request.
- **Refresh**: when a request 401s, call `POST /api/v1/auth/refresh` with the
  stored refresh token; store the *new* pair it returns (the old refresh token
  is now invalid — rotation). If refresh itself 401s, force re-login.
- **Logout**: `POST /api/v1/auth/logout` (current session) or `/logout-all`
  (all devices).
- **WebSocket chat**: connect to
  `wss://<host>/api/v1/ws/chat/{conversation_id}?token=<access_token>` (token
  passed as a query param since browser/Flutter WS clients can't always set
  headers on the handshake). Send `{"content": "..."}` text frames; messages
  from any participant (including sent via the REST endpoint) are pushed to
  all connected sockets for that conversation via Redis pub/sub, so it works
  the same whether the mobile app is talking to the same server process or a
  different one behind a load balancer.
- **File uploads**: multipart/form-data with a single `file` field to the
  relevant `.../photo`, `.../media`, or `.../images` endpoint; the response
  includes the resulting public URL.
- **Pagination**: paginated list endpoints return
  `{items, total, page, page_size, pages}`; pass `page` / `page_size` query
  params.
